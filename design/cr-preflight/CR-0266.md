# CR-0266 Implement the Shared Application Command Registry Foundation

Status: CLOSED

## Functional Inventory

- Freeze a C-compatible registry API and immutable command metadata contract.
- Represent stable lowercase dotted IDs, labels, descriptions, schemas,
  permission classes, handler identity, state effect, and recordability.
- Support deterministic lookup, complete enumeration, duplicate rejection, and
  bounded argument/result representations.
- Keep semantic execution distinct from GUI parameter acquisition and file
  dialogs.
- Provide a dispatch boundary that application/orchestrator code can serialize
  on the machine-owning thread; registry lookup itself must not mutate machine
  state.

## Frozen API Decision

The registry is an application-layer C API. Commands are immutable after
registration, IDs and metadata are borrowed read-only strings, and a registry
owns only the supplied command table and bounded dispatch context. The result
contract is a tagged status plus a stable reason token and optional bounded
message; semantic handlers receive an opaque application context and a
validated argument view. Handler code is responsible for orchestration and
serialization, not the registry lookup layer.

The initial API surface is:

```text
wz_command_registry_init
wz_command_registry_register
wz_command_registry_finalize
wz_command_registry_find
wz_command_registry_count
wz_command_registry_at
wz_command_registry_dispatch
```

Registration rejects malformed IDs, missing metadata, duplicate IDs, invalid
permission classes, and null handlers. Finalization makes enumeration and
lookup stable. Dispatch rejects unknown or unavailable commands before calling
the handler and never acquires GUI parameters or host paths.

## Disposition

| Surface | Disposition | Reason |
|---|---|---|
| Registry metadata and lookup | IMPLEMENT_NOW | Required Phase-12A foundation |
| Result/error contract | IMPLEMENT_NOW | Shared by GUI, tests, and later remote projection |
| Semantic handler execution | IMPLEMENT_NOW | Establishes one dispatch boundary |
| GUI/file-dialog parameter acquisition | DEFER_TO_UI_CR | Front-end responsibility |
| Complete command/menu population | DEFER_TO_FOLLOWING_CR | Requires separate legacy action inventory slices |
| Telnet parser and transport | DEFER_TO_PHASE_15 | Separate transport boundary |

metadata and result structures, verify invalid and unavailable paths, and check
that fixed-argument menu actions can later bind to one semantic handler. Scan
the include graph to prove no deterministic-core header depends on the
application registry and that dispatch does not mutate state during lookup.
