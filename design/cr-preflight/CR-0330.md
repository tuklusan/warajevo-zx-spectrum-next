## Change Request
CR-0330: Require clear loss disclosure before lossy conversions

Status: CLOSED
Priority: low

## Functional Inventory
- Identify every Compatibility Tools conversion entry that can discard,
  normalize, or otherwise change source information.
- Expose a stable, machine-readable disclosure requirement before a conversion
  can be selected or executed.
- Present a clear human-readable warning that conversion may change or discard
  machine-visible or source-format information.
- Keep native load/run routes separate from conversion routes; native loading
  must never acquire an implicit conversion confirmation.
- Keep conversion execution host-side and atomic, with no deterministic machine
  state mutation in this catalog/API change.
- Preserve unavailable/later-tool reasoning and shared command identity.

## Upstream Discovery
- UI architecture sections 7.1, 8.1, 12.3, 15.5, 17, 19, 20.6-20.18,
  and 22.2-22.3 define explicit conversion presentation and loss disclosure.
- Core architecture sections 23, 25.1-25.3, 28.7, 41, 44, 49.1, and 49.2
  define representability, atomic failure, and host-data safety boundaries.
- `design/media-format-support.md` and `design/migration-ledger.md` remain
  the format and provenance authorities.
- The existing Compatibility Tools catalog and route API are the only seams
  required for this metadata-only increment.
- Preserved Warajevo conversion menu/routine descriptions were checked so the
  disclosure is not limited to one modern file extension.

## Disposition
`IMPLEMENT_NOW`: add explicit loss-disclosure metadata and a stable query
function to the existing Compatibility Tools catalog. Do not implement a
converter, silently convert, or mutate native load behavior.

## Zero-Gap Exit Scan
Re-read the cited UI/core sections and the preserved conversion inventory after
implementation. Confirm that every currently cataloged conversion has a
non-empty disclosure, native routes remain disclosure-free, and no conversion
can be presented as lossless by omission.
