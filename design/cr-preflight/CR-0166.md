# CR-0166 Preflight: TZX Container and Block Parsing

Status: APPROVED_FOR_IMPLEMENTATION

## Objective

Implement bounded parsing of the frozen supported TZX container and block
classification without conflating TZX with standard or native TAP. The parser
must validate every declared length before exposing block views and must return
controlled errors for malformed supported blocks and unsupported block kinds.

## Functional Inventory

- Validate the TZX signature, version bytes, and complete block boundaries.
- Parse the frozen supported blocks: standard speed data, turbo speed data,
  pure tone, pulse sequence, pure data, direct recording, CSW, generalized
  data, pause, group start/end, jump, loop, call/return, select, stop-if-48K,
  signal level, and glue blocks as defined by the media matrix.
- Classify metadata blocks as ignored without allowing their bytes to alter
  machine input, and classify reserved or unknown blocks as unsupported.
- Validate variable-length fields, jump/call/loop targets, and terminating
  control paths before allocation or state publication.
- Preserve bounded caller-owned block views and deterministic block ordering;
  defer timing execution to the next ordered TZX timing task.
- Keep standard TAP and Warajevo-native TAP routing and writers unchanged.
- Add deterministic signature, truncation, classification, control-target,
  and no-partial-publication coverage.

## Upstream Discovery

The architecture and media matrix define the TZX classification and controlled
error policy. The preserved upstream source is the provenance authority for
any legacy container details found during implementation; scan it before code
changes and repeat the scan before closure. This CR owns parsing and
classification only, not tape-edge execution or host file I/O.

## Disposition

Implement only TZX container validation, bounded block views, classification,
and deterministic rejection behavior. Do not implement TZX timing/control
execution, WAV decoding, native or standard TAP changes, instant loading,
trap detection, or host file-system behavior.

## Zero-Gap Exit Scan

Before closure, repeat the upstream and matrix comparison against every listed
block family, length rule, classification, and control-path validation. Close
only when each behavior is implemented or assigned to a later ordered task,
with serialized reviews, remote validation, the full hosted matrix, clean
repository gates, and published evidence.

## Verification Plan

- Static repository gates and source inspection on the development machine only.
- Serialized pre-development and final CODE/DOCUMENTATION reviews.
- Remote Linux and Windows smoke builds/tests through the parser-validated
  project harness.
- Hosted `platform-smoke` validation across all configured runner lanes.
- No local build or test execution.
