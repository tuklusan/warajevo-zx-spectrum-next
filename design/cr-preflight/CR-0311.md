## Change Request
CR-0311: Implement Tape Manager block operations

Status: APPROVED_FOR_IMPLEMENTATION
Priority: medium

## Functional Inventory
- Provide one media-manager backend for reorder, extract, add/import, delete,
  edit-where-permitted, copy-to-new, and change-position operations.
- Preserve deterministic block ordering and selection semantics across operations.
- Reject invalid indexes, empty/oversized blocks, unsupported edits, read-only
  destinations, and insufficient caller capacity without partial mutation.
- Keep the original image unchanged until an operation has completed successfully;
  serialization/atomic replacement remains the later task 309 boundary.
- Keep the backend independent of GUI toolkit, host dialogs, and emulator timing.

## Upstream Discovery
UI architecture sections 12.2, 12.5, 20.1, 20.2, 45, and 48 define the complete
operation set and failure behavior. Developer task 306 is the derived backlog item.
The canonical media parser types in `src/core/wz_tape.h` provide caller-owned TAP
block data and the existing Tape Manager presentation model in
`src/app/wz_tape_manager.h` provides the presentation boundary. No operation in
the required list remains undispositioned.

## Disposition
`IMPLEMENT_NOW`: add a bounded caller-owned block-edit backend shared by the Tape
Manager operations. It will use transactional working storage supplied by the
caller and will not write host files or alter machine state. Format-specific
serialization and atomic file replacement remain explicitly deferred to later
media tasks.

## Zero-Gap Exit Scan
Confirm every Section 12.2 operation has an API and regression coverage, selection
and ordering are stable, all failure paths leave caller data unchanged, edits are
bounded, and no GUI/host-dialog/core-state dependency is introduced.
