## Change Request
CR-0301: Make host output creation and atomic replacement interprocess-safe

Status: CLOSED
Priority: high

## Functional Inventory
- Provide one host-only atomic output-write boundary for generated persistent files.
- Create each temporary output with exclusive creation and a process/attempt-unique name.
- Write and flush the complete temporary file before publishing it.
- Replace the destination atomically, never exposing a partial output.
- Permit concurrent writers to serialize by replacement or fail cleanly, without interleaving.
- Remove temporary residue on all failure paths.
- Preserve destination contents when a write fails before replacement.
- Support Windows and POSIX host APIs without entering deterministic core state.
- Keep path, file bytes, and host synchronization data outside machine state.
- Retain the existing configuration safety contract while making the policy reusable by screenshots, snapshots, conversions, and exports.

## Upstream Discovery
Core Section 28.7 requires every WZSN-managed persistent output to use an
exclusive destination claim or atomic write-to-new-file/replace protocol.
UI Sections 44.1 and 49.1 apply the same rule to screenshots, snapshots,
conversions, and exports. The existing `wz_host_config_write_atomic` seam
demonstrates platform-specific temporary writing but is configuration-specific
and not reusable by other output workflows. The preserved upstream source was
searched for atomic output, replacement, temporary output, and concurrent
writer behavior; no portable equivalent exists. No upstream behavior remains
undispositioned.

## Disposition
`IMPLEMENT_NOW`: add a generic host output writer with unique temporary files,
complete flush, and atomic replacement, then cover its failure and concurrent
writer invariants with remote-executed tests. Existing configuration code
remains behavior-compatible; later workflows adopt this boundary instead of
implementing their own file commit logic.

## Zero-Gap Exit Scan
Confirm unique temporary creation, complete flush before publication, atomic
replacement on Windows and POSIX, no partial destination visibility, clean
failure residue handling, concurrent-writer behavior, and no deterministic-core
or harness dependency.
