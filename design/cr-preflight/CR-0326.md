## Change Request
CR-0326: Implement Debugger/Monitor window over shared Phase-11 debugger APIs

Status: APPROVED_FOR_IMPLEMENTATION
Priority: medium

## Functional Inventory
- Provide a first-class Debugger / Monitor window reachable from the existing
  `Tools > Debugger...` semantic command and toolbar entry.
- Present execution control, registers, flags, interrupt state, disassembly,
  memory inspection/editing, breakpoints, paging, device/diagnostic state, and
  trace/log views as distinct UI surfaces over one live machine.
- Reuse `wz_debugger_snapshot`, memory/disassembly/page APIs, breakpoint and
  execution controls, and the existing trace boundary; do not create a second
  CPU, memory array, scheduler, or emulator.
- Keep read-only inspection valid while running; require the core's explicit
  paused mutation boundary for register, memory, paging, breakpoint, step, and
  continue controls, with operation results and disabled reasons visible.
- Preserve exact register/flag/interrupt values, model/paging state, and
  disassembly address/length semantics without host paths or host state entering
  canonical machine state.
- Keep debugger window open/close, selection, display preferences, and refresh
  state in host/UI state only; opening the window must not reset, pause, advance,
  or otherwise mutate the machine.
- Ensure GUI, toolbar, Telnet, and automated-test projections continue to use
  the shared command registry and identical availability predicates.

## Disposition
`IMPLEMENT_NOW`: add a project-owned debugger-window presentation model and
shared-command integration over the existing Phase-11 debugger APIs. Keep all
machine semantics in the core and do not modify frozen harnesses or wrappers.
