# CR-0284 Registry-Driven UI Enabled State

Status: CLOSED
Priority: HIGH
Execution order: ARCHITECTURE_2_PHASE_12H
Blocking: NO

## Functional Inventory

- Expose a UI query for whether a semantic toolbar/menu command is enabled.
- Delegate the query to the command registry availability predicate and return
  its disabled reason without duplicating predicate logic in the UI.
- Treat a missing command, an unfinalized registry, or an unavailable command
  deterministically and without dispatching or mutating machine state.
- Keep semantic command IDs independent of labels and cosmetic GUI structure.
- Cover enabled, unavailable-with-reason, missing-command, and unfinalized
  registry cases in focused acceptance tests.

## Upstream And Architecture Discovery

- UI Architecture Sections 7, 8, 24, 35, and 48.3-8 require one shared
  registry, stable IDs, registry-owned availability predicates and reasons,
  consistent GUI/Telnet state, and remote-permission separation. Task 280 is
  the explicit toolbar/menu binding step.
- The legacy reference has menu enablement concepts but no modern shared
  registry API; its behavior is used only to enumerate state distinctions, not
  to justify private UI predicates.
- Existing `wz_command_registry` already owns the availability callback used by
  dispatch. The new layout projection must call that same callback and must not
  invoke handlers or create a second state authority.
- No deterministic core, transport, harness, or wrapper changes are allowed.
